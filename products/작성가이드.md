## 1. 왜 이 문서를 씁니까

위세아이텍 **영업 지원 스테프**(사업제안서 통합관리 시스템)는 RFP(제안요청서) PDF를 읽어
요구사항을 뽑아내고, **이 저장소의 제품 문서를 근거로** 제안서 초안 PPT를 자동으로 만듭니다.

```
RFP PDF → 요구사항 자동 추출 → [ 이 저장소의 제품 지식과 매칭 ] → 제안서 PPT 자동 생성
```

즉,

- **여기에 없는 제품은 제안서에 나오지 않습니다.**
- 여기에 적힌 문장이 곧 제안서 본문의 근거가 됩니다. 두루뭉술하게 적으면 두루뭉술한 제안서가 나옵니다.
- 현재 [`와이즈AIOps/`](./와이즈AIOps/) 만 상세 수준으로 채워져 있고, 나머지 제품은 개요 수준입니다.

그리고 제안 현장에서 **제품 소개서·매뉴얼·서버 사이징·이중화 스펙·요구사항 수용 여부·M/M 및 일정 산정**을
반복해서 요구받습니다. 요구가 올 때마다 제품 담당자를 찾아 물어보는 일을 없애기 위해,
같은 제품 폴더 안에 [제안 대응 문서 4종](#4-제안-대응-문서-4종--소개서--매뉴얼--사이징--제안대응)도 함께 관리합니다.

## 2. 무엇을 올립니까 — 제품 폴더 하나

제품 하나당 폴더 하나입니다. 앞의 3종(`README.md`·`slides.md`·`images/`)은 시스템의
**제품 지식 매핑 화면(KB 스튜디오)** 과 1:1로 대응하고, 뒤의 4종은 **영업·제안 현장에서 반복해서
요구받는 자료**입니다.

```
products/
└── 와이즈AIOps/              ← 제품 = KB 화면의 제품 선택
    ├── README.md            ← 「기능」 탭  : 제품 설명·기능 계층
    ├── slides.md            ← 「슬라이드」 탭: 요구사항 ↔ 대응 문장 ↔ 원본 ppt 위치
    ├── images/              ← 「이미지」 탭 : 제품 화면 캡쳐 png
    │   └── workflow-canvas.png
    ├── 소개서.md             ← 제품 소개서·리플릿 위치와 소개 논리
    ├── 매뉴얼.md             ← 매뉴얼 목록·제공 범위·기술지원 조건
    ├── 사이징.md             ← 데이터 용량별 서버 스펙 · 이중화 구성
    └── 제안대응.md           ← 요구사항 수용 여부 판정 · M/M·일정 산정
```

### 시스템(KB)이 읽는 3종 — 제안서 자동 생성의 근거

| 파일 | KB 화면 | 제안서 생성에서 쓰이는 방식 |
|------|---------|------------------------------|
| `README.md` | 기능 | `### 대분류 → #### 중분류` 단위로 잘려 **검색 단위(청크)** 가 됨. RFP 요구사항과 의미가 가까운 청크가 근거로 주입됨 |
| `slides.md` | 슬라이드 | 어떤 요구사항에 어떤 기성 슬라이드가 대응하는지의 지도. 담당자가 원본 pptx를 찾아 반영 |
| `images/` | 이미지 | 본문에 삽입된 이미지가 제안서 슬라이드 삽화 후보가 됨. **alt 텍스트**가 함께 읽힘 |

### 사람이 찾아 쓰는 4종 — 제안 대응 문서

| 파일 | 언제 필요한가 | 없으면 생기는 일 |
|------|---------------|------------------|
| `소개서.md` | 사전규격·영업 초기에 "제품 소개서 주세요" | 담당자를 찾아 물어보고, 어느 버전이 최신인지 매번 확인 |
| `매뉴얼.md` | 제안서 기술지원·교육 항목 작성 시 | 매뉴얼이 있는지조차 몰라 "제공 예정"으로 뭉뚱그림 |
| `사이징.md` | "데이터가 O TB인데 서버 몇 대냐", "이중화하면 스펙이 어떻게 되냐" | 회신이 며칠 늦고, 사람마다 다른 수치를 답함 |
| `제안대응.md` | 요구사항정의서를 받아 항목별 수용 여부·공수를 회신할 때 | 수용 가능한지 몰라 과다 산정하거나, 반대로 안 되는 걸 수용해버림 |

> 4종은 **제안 대응 속도를 위한 문서**입니다. 자동 생성에 바로 쓰이지는 않지만,
> 요구가 들어올 때마다 담당자를 붙잡지 않고 이 문서만 보고 답할 수 있게 하는 것이 목적입니다.

> ⚠️ **이 저장소는 공개(public) 입니다.**
> 제안서 원본(pptx)·고객 제안 내용·계약 금액·고객 실데이터 화면은 **올리지 마세요.**
> 제안 슬라이드는 원본 대신 `slides.md` 에 "요구사항명 · 대응 핵심 문장 · 원본 위치"만 적습니다.

## 3. KB 문서 3종 작성법 — 3단계

### 1단계. 제품 문서 (`README.md`) — 필수

[`_양식/README.md`](./_양식/README.md) 를 복사해 채웁니다. 예시: [`와이즈AIOps/README.md`](./와이즈AIOps/README.md)

**기능 계층을 반드시 지켜주세요.** 이 계층이 그대로 검색 단위가 됩니다.

```markdown
## 2. 주요 기능

### 2.1 Data Manager              ← 대분류(모듈)
데이터 수집·저장·조회·스케줄링 등 데이터 라이프사이클 관리 모듈.

#### 데이터셋 관리                 ← 중분류(기능군)
- **데이터셋 추가**: 연결관리에 등록된 저장소에서 테이블 또는 파일을 통해 데이터셋을 생성하는 기능
- **데이터셋 API 공유**: 데이터셋을 API로 공유하는 기능
  - 지원 소스: 스토리지 · 하이브 · 데이터베이스 · SFTP/FTP · API   ← 세부 옵션은 `·` 로 나열
```

|  | 좋은 예 | 나쁜 예 |
|--|---------|---------|
| 기능 설명 | `- **스케줄 등록**: 생성한 워크플로우를 스케줄에 등록하여 자동으로 실행할 수 있도록 하는 기능` | `- 스케줄 기능 제공` |
| 분량 | 중분류당 소분류 3~8개, 각 한 문장 | 표 한 줄로 "주요 기능: 데이터 관리, 모델 관리" |
| 용어 | RFP에 나오는 말(요구사항 용어)로 | 사내 코드명·약어만 |

마지막 `## 제안서 작성 시 강조 포인트` 섹션은 **제품 공통 문구로 항상 주입**되므로 꼭 채워주세요.

### 2단계. 화면 캡쳐 (`images/`) — 권장

- 파일명은 `대분류-중분류[-세부]` 영문 케밥케이스: `data-manager-dataset.png`
- 본문 삽입 시 **alt 텍스트에 화면 내용을 요약**해 적습니다 (이 텍스트가 제안서에 반영됩니다).

```markdown
![데이터셋 관리 화면 — 등록된 데이터셋 목록과 통계 정보](./images/data-manager-dataset.png)
```

자세한 규칙: [`_양식/images/README.md`](./_양식/images/README.md)

### 3단계. 제안 슬라이드 인덱스 (`slides.md`) — 기성 제안 슬라이드가 있는 경우

이미 만들어 둔 제품 제안 슬라이드가 있으면, **원본 pptx는 올리지 말고** 아래만 적습니다.

```markdown
### 1. 플랫폼 데이터 수집 방법          ← 요구사항명 = pptx 파일명

- **대응 핵심 문장**: 다양한 데이터 소스(RDBMS, Hadoop, Flat File, Hive Query, 실시간 데이터)에서
  데이터를 수집하여 플랫폼에 저장, GUI 기반으로 수집 프로세스를 손쉽게 설계
- **구성**: 1) 워크플로우 수집 지원 컴포넌트 · 2) 웹 GUI 기반 워크플로우 개발 관리
- **레이아웃 유형**: `process`
- **원본 위치**: `사내 NAS /제안자산/WiseAIOps/플랫폼 데이터 수집 방법.pptx` (슬라이드 1장)
```

- 양식: [`_양식/slides.md`](./_양식/slides.md) · 완성 예시: [`와이즈AIOps/slides.md`](./와이즈AIOps/slides.md)
- **한 슬라이드 = 한 요구사항**, 파일명은 RFP 요구사항 표현으로 (`플랫폼 데이터 수집 방법`, `모델 서빙 방법`).
- 고객사·사업명·특정 도메인 용어는 일반화해서 적어주세요 (`○○공사 배관 경로` → `설비 경로`).
- 원본 pptx는 사내 담당자에게 별도로 전달하면 시스템에 등록됩니다.

## 4. 제안 대응 문서 4종 — 소개서 · 매뉴얼 · 사이징 · 제안대응

각 제품 폴더에 **빈 스켈레톤이 이미 들어가 있습니다.** 새로 만들 필요 없이 열어서 `[ ]` 자리를 채우면 됩니다.
양식 원본은 [`_양식/`](./_양식/) 에 있습니다.

> 📌 **작성 원칙 — 모르는 값은 비워두지 말고 상태를 적으세요.**
> 빈칸은 "확인 안 됨"인지 "해당 없음"인지 구분이 안 됩니다.
> `미보유` · `미지원` · `별도 협의` · `확인 중(담당: 홍길동)` 처럼 상태를 적어주세요.

### 4-1. `소개서.md` — 제품 소개

가장 자주 요구받는 자료입니다. **소개서 원본 파일은 올리지 말고 위치만** 적습니다(공개 저장소).

- 한 장 요약: 영업 담당자가 고객에게 그대로 읽어줄 수 있는 수준의 한 문장 정의 + 핵심 가치 3개
- 소개서 원본 표: 자료명 · 버전 · 분량 · 보관 위치 · 최종 갱신 · **대외 공개 가능 여부**
- 고객 유형별(공공/금융/제조) 앞세울 논리, 경쟁 제품 대비 차별점, 공개 가능한 레퍼런스, 인증·특허, FAQ

### 4-2. `매뉴얼.md` — 매뉴얼 안내

제안서의 **기술지원·교육·유지보수 항목**을 쓸 때 근거가 됩니다. 매뉴얼 원본은 올리지 않습니다.

- 매뉴얼 목록: 설치·관리자·사용자·운영·API 규격서·릴리즈 노트 (없으면 **"미보유"** 로 명시)
- 제공 형태(형식·시점·부수·갱신 주기), 설치 전제조건 요약, 교육 과정, 기술지원 SLA

### 4-3. `사이징.md` — 서버 사이징 및 이중화 ⭐ 요구 빈도 최상

"데이터가 O TB인데 서버가 몇 대 필요하냐", "이중화하면 스펙이 어떻게 되냐"에
**표를 보고 바로 답할 수 있게** 적는 것이 목표입니다.

- **산정 전제** 먼저 — 데이터 증가율·보존 기간·동시 사용자·가상화 여부. 전제가 다르면 답이 달라집니다
- **데이터 용량별 서버 스펙** 표 — 소/중/대/초대 구간별 서버 수·CPU·Memory·디스크
- **이중화 구성** — 컴포넌트별 Active-Active / Active-Standby, 추가 서버 수, RTO·RPO
- **이중화 시 산정 규칙** — "서버가 두 배냐"에 답하는 부분. 필요한 부대 요소(L4·공유 스토리지 등)와
  **이중화 시 라이선스 추가 여부**를 반드시 적어주세요. 견적에 직결됩니다
- 스토리지 산정식(원천 대비 배수 + 인덱스·로그·백업·여유율), SW 요구사항, 라이선스 정책

> 공공 제안에서는 **국산 DBMS·국산 OS 지원 여부**와 **폐쇄망 설치 가능 여부**를 특히 자주 확인합니다.

### 4-4. `제안대응.md` — 수용 여부 및 M/M·일정 산정

요구사항정의서를 받았을 때 항목별로 회신하기 위한 문서입니다.

- **판정 등급**(전 제품 공통): `기본` · `설정` · `개발` · `연계` · `미지원`
- **요구사항 유형별 판정 표** — 그동안 받아본 요구를 유형으로 묶어 미리 판정해 둡니다
- **미지원·제약 사항** — 불리한 항목일수록 미리 적어주세요.
  제안 단계에서 모르고 수용했다가 구축 단계에서 문제가 되는 경우가 가장 큽니다
- **M/M 원단위** — 설치 1식, 연계 1건, 화면 1개, 리포트 1건, 이행 1TB, 안정화·PM 비율
- **표준 일정(WBS)** 과 최소 수행 기간, 산정 예시

> 원단위가 있으면 요구사항 개수만 세어도 대략의 공수가 나옵니다.
> 정밀 산정이 아니라 **초기 회신 속도**가 목적입니다. 실제 제안 공수는 담당 사업부가 최종 검토합니다.

## 5. 올리는 방법

### 방법 A. GitHub 웹에서 (Git을 안 쓰는 경우)

1. https://github.com/rnd-wiseitech/company-docs 접속 → `products` 폴더
2. `_양식` 폴더의 파일들을 열어 `Raw` 복사
3. `Add file → Create new file` → 파일명에 `제품명한글/README.md` 입력 (`/` 를 치면 폴더가 생깁니다)
4. 내용 붙여넣고 수정 → 아래 **Create a new branch ... and start a pull request** 선택 후 Propose changes
5. 이미지는 `Add file → Upload files` 로 `제품명한글/images/` 에 올립니다

### 방법 B. Git으로

```bash
git clone https://github.com/rnd-wiseitech/company-docs.git
cd company-docs/products
cp -r _양식 와이즈○○          # 제품명 한글로 폴더 생성
# README.md / slides.md 작성, images/ 에 캡쳐 추가
git checkout -b docs/와이즈○○
git add . && git commit -m "docs(products): 와이즈○○ 제품 지식 작성"
git push origin docs/와이즈○○   # → GitHub에서 Pull Request 생성
```

## 6. 올린 뒤에 일어나는 일

1. 관리자가 시스템의 **관리자 → PPT 생성 설정 → `KB 동기화`** 를 실행합니다.
2. 시스템이 이 저장소의 `products/<제품>/README.md` 와 이미지를 내려받아 문장 단위로 색인합니다.
3. **제품 지식 매핑** 화면에서 제품별 슬라이드·기능·이미지가 보이고, 요구사항 키워드와 수동 매핑도 걸 수 있습니다.
4. 이후 생성되는 제안서부터 해당 제품 근거가 반영됩니다.

> 동기화는 관리자만 실행합니다. 올린 뒤 사내 담당자에게 알려주세요.

## 8. 자주 묻는 질문

**Q. 제품 소개서 PPT를 그냥 올리면 안 되나요?**  
A. 안 됩니다. 공개 저장소이고, 시스템이 검색하는 단위는 "기능 문장"입니다.
PPT 문구를 그대로 옮기더라도 `### / #### / -` 계층으로 풀어서 적어주세요.

**Q. 기능이 너무 많은데 어디까지 적나요?**  
A. RFP 요구사항으로 나올 만한 것은 모두 적는 게 좋습니다.
와이즈AIOps 기준 6개 모듈 · 약 100개 소분류 기능이 적혀 있습니다.

**Q. 제품 버전이 올라가면요?**  
A. 같은 파일을 수정하고 상단 `최종 수정일`을 갱신하면 됩니다. 다음 동기화 때 반영됩니다.

**Q. 우리 제품은 아직 폴더가 없습니다.**  
A. `_양식` 폴더를 통째로 복사해 `products/<제품명 한글>/` 로 만들면 됩니다.

**Q. 사이징 수치를 확정해서 적기가 부담스럽습니다.**  
A. 표준 구성 기준값이면 됩니다. 각 문서 하단에 "실제 제안 시 담당 사업부 검토를 거친다"는
단서가 이미 들어가 있습니다. 아무 값도 없는 상태가 가장 나쁩니다 — 요구가 올 때마다
처음부터 다시 산정하게 됩니다.

**Q. 제안 대응 문서 4종도 제안서 자동 생성에 쓰이나요?**  
A. 현재는 아닙니다. `README.md`·`slides.md`·`images/` 3종이 자동 생성에 쓰이고,
4종은 사람이 찾아 쓰는 자료입니다. 다만 사이징·수용 여부는 제안서 본문에도 자주 들어가므로
향후 생성에 반영할 예정입니다.

**Q. ASTA와 코드인슈어는 왜 없나요?**  
A. 두 제품은 이 저장소와 영업 지원 스테프의 관리 대상이 아닙니다(2026-08 제외).
